Design system, components & layouts

This is everything that has to be agreed before production code starts. It covers the visual language, every reusable component and the data rules that control it, the key page layouts (mobile-first), the trip/departure data model, campaign deep links, the Razorpay-ready booking flow and the SEO intent map.

Conversion → Trust → Mobile → SEO → Performance → Polish → Animation
All trip names, prices, dates, seat counts and reviews on this page are sample content to show how components behave. None of it will ship. Each component lists the data rule that decides whether it shows. Coloured blocks marked "PHOTO" stand in for real HCC photography.
01 · Brand direction

"Field-tested, not brochure"

Generic travel agencies look the same: blue skies, gradient buttons, stock couples with suitcases, sixteen badges. HCC should feel closer to a premium outdoor-gear brand that also runs trips. It's confident, calm and specific. The premium feel comes from restraint, real photography and precise information design, not from effects.

Five signature elements that make it HCC (and nobody else)

1 · Ticket-stub duration
2N3D

Duration reads like a trip ticket. It's used on every card and hero, so the duration is always the first thing you see.

2 · Route line

3 · Boarding-pass dates

4 · Contour texture

Deep forest sections carry a faint topographic map line.

A 1 KB SVG pattern. It gives depth with no images and no gradients.

03 · Primitives

Buttons, badges, chips, forms

Buttons

Labels always say what happens next ("View Dates", "Book Your Seat", "Get Full Itinerary", "WhatsApp HCC", "Plan My Trip"). No "Click here", "Submit" or "Learn more". Minimum height is 48px (40px for compact buttons inside cards).

Badges: status is always data-driven

6 seats left Filling fast Sold out Waitlist open New dates added Long weekend Easy trek Weekend
  • "N seats left" renders only when the team has entered seatsLeft on that departure and it is ≤ the threshold in Settings (default 8).
  • "Filling fast" renders only when the team ticks fillingFast. It is never computed or random.
  • If both are present, only the seat count shows. There is at most one urgency badge per card.
  • No countdown timers, "X people viewing" or auto-popups.

Filter chips & segmented controls

  • Month chips are generated from months that have open departures. An empty month never appears.
  • The city chip (Hyderabad / Bangalore) only renders when departures exist from more than one city.

Form fields

Labels sit above fields (never placeholder-only), inputs are 16px to stop iOS zoom, and fields use the right keyboard type (tel, numeric). Errors are inline and specific. Required fields are kept to 2 (name and phone).

06 · Data architecture

One trip, many departures

A Trip holds everything that is true for every date: story, itinerary, inclusions, stays and options. A Departure is one dated instance and holds only what changes: date, origin, price overrides, seats and status. The marketing team edits departures 20× more often than trips, so they get their own simple list in the CMS.

Destination ~30

  • slug, name, region, state
  • distanceFromHyd, howToReach[]
  • bestMonths[], idealDuration
  • experiences[], faqs[], nearby[]
  • seo, indexable

Trip 50–100+

  • slug (ooty-coonoor), title, tripTypes[]
  • destinations[] → Destination
  • origins[]: city, pickupPoints[], arrival/return legs, indexable
  • transportOptions[]: id, mode, class, priceDelta
  • stayOptions[]: id, sharing, property, washroom, priceDelta
  • basePrice, originalPrice?, advanceAmount, gstPercent
  • itinerary[], inclusions[], exclusions[], faqs[]
  • recurrence? ("Every Friday"), status, seo

Departure edited weekly

  • id (ooty-coonoor-hyd-2026-10-09)
  • trip → Trip, origin (must exist on the trip)
  • startDate, endDate
  • price? / originalPrice? (override)
  • optionPrices? (per transport/stay override)
  • availableOptions? (e.g. no twin this date)
  • seatsTotal?, seatsLeft?, fillingFast?
  • status: open · waitlist · soldout · closed · cancelled
  • bookingMode?: enquiry · payment (defaults from Settings)
  • note? ("Diwali special")

Review

  • name, rating, text, date
  • source (google · instagram · direct), sourceUrl
  • trip?, destination?, photo?
  • consent: true (required)

Guide · Author

  • category, tags[], author, publishedAt, updatedAt
  • relatedTrips[], relatedDestinations[]
  • quickAnswer, faqs[], body (MDX)

Collection

  • slug, title, intro, body, faqs
  • rule: tripTypes / destinations / months / maxNights
  • activeFrom?, activeUntil? (seasonal)

Settings (singleton)

  • announcement, contact, NAP, hours
  • stats[] (hide if empty), trust claims[]
  • payments {enabled, provider, advanceDefault}
  • urgency {seatThreshold}
  • tracking IDs

Price & availability resolution (one function, used everywhere)

// resolvePrice(trip, departure, {transport, stay})
price = departure.optionPrices?.[transport+stay]
     ?? (departure.price ?? trip.basePrice)
        + trip.transportOptions[transport].priceDelta
        + trip.stayOptions[stay].priceDelta

// "From ₹" on any card / page / schema
fromPrice(trip, origin) = min(resolvePrice(...))
  over departures where origin matches
  and status ∈ {open, waitlist}
  and startDate > today
  across that departure's availableOptions

// seats badge
showSeats = d.seatsLeft != null
         && d.seatsLeft <= settings.urgency.seatThreshold
         && d.status == "open"

07 · Campaign deep links

Ads link to real pages, not copies

No separate landing pages per campaign. Every ad points at the canonical trip (or collection) URL plus parameters. The page adapts to the parameters, attribution is stored, and the canonical tag stays clean, so there's no duplicate content.

Rules

  • Canonical is always the clean path (no params). Parameterised URLs are never in the sitemap.
  • Message match: the ad's date/price is visible above the fold on mobile without scrolling (verified at 375px).
  • Optional short links for Instagram bio/stories: /go/ooty → 302 to the full URL with UTMs. These are entries in one redirects file, not pages.
  • WhatsApp ref code: [ref: OOTY-1009 · ig] is appended to the pre-filled message, so chats are attributable without asking the customer.
  • UTMs are not added to internal links (that would break GA4 sessions). The stored values carry attribution instead.

08 · Booking architecture

Enquiry now, Razorpay later, same pipe

Every conversion action (Book, Get Itinerary, Plan My Trip, Contact) creates one kind of record, a BookingIntent (lead), through one endpoint. Payment is a later step on that same record, so adding Razorpay is an adapter plus a webhook, not a rebuild.

BookingCard / EnquiryForm→ POST/api/intents→validate + attach attribution→store (Sheet / DB)→notify team (WhatsApp/email)→Meta CAPI + GA4 MP
responsenext: "confirm"→ thank-you + "Continue on WhatsApp"next: "pay" (later)→ Razorpay Checkout → webhook → status: paid
